# Tomi for Apple (iOS, then macOS)

Tomi's Apple clients, written in SwiftUI, at the same functional level as the Android client. Like Android, they
call the Rust core `tomi-core` through UniFFI bindings: no cryptographic primitive, no network access, and no sensitive
storage is written in Swift.

A single Xcode project (generated from `project.yml`) holds the iOS targets and, later, the macOS targets; shared code
lives in local SwiftPM packages. Implementation specification, milestones and conventions:
[`docs/archive/apple-spec-implementation.md`](../../docs/archive/apple-spec-implementation.md).

## Structure

```
apps/apple/
  project.yml               # XcodeGen → Tomi.xcodeproj (ignored by git)
  Config/                   # xcconfig (Debug, Release); Signing.local.xcconfig and Local.xcconfig (default relay) are ignored
  Tomi/                     # iOS app target (SwiftUI); macOS later in the same project
  TomiShare/                # iOS share extension
  Packages/
    TomiCore/               # the Rust core for Swift (UniFFI bindings + generated XCFramework)
    TomiKit/                # pure logic (model, detection, filters, tap per type…), testable on macOS
    TomiDesign/             # design charter: colours, typography, logo, base components
    TomiRuntime/            # core adapter (real or demo), Keychain, paths, send queue; shared with the extension
  tools/build-core.sh       # builds the XCFramework and the generated Swift (`just apple-core`)
  tools/simulator-udid.sh   # identifier of the « iPhone Duo » simulator (two share this name, so `name=` is ambiguous)
```

Status: the foundation exists and the app shows a themed shell on the demo core. The screens are being built
against the specification.

Two files are **generated from their sources of truth** and committed (Xcode needs them); do not edit them by hand:

- `Packages/TomiDesign/Sources/TomiDesign/TomiTokens.swift` ← `design/tomi/tokens.json` (`tools/tokens-to-swift.py`);
- `Tomi/Resources/Localizable.xcstrings` ← `apps/android/app/src/main/res/values/strings.xml` (`tools/strings-from-android.py`),
  same keys and same texts as Android.

`Tomi.xcodeproj` is generated by XcodeGen from `project.yml` and is not committed. The app's demo files are the Android
demo assets (`apps/apple/DemoAssets/demo`), referenced by path and excluded from Release builds.

## Prerequisites

- Xcode 27 with the iOS SDK and an « iPhone Duo » simulator (reference); `xcodegen` (`brew install xcodegen`).
- Rust via **rustup** (not Homebrew's `rust`), toolchain 1.99 (the one used in CI), and the targets:

```sh
rustup target add aarch64-apple-ios aarch64-apple-ios-sim x86_64-apple-ios
```

## Build and test

```sh
just apple-core          # the Rust core as an XCFramework (do this first)
just apple-project       # tokens, strings, then Tomi.xcodeproj (xcodegen)
just apple-test          # all Apple tests (macOS, then the iPhone Duo simulator)
open Tomi.xcodeproj      # Xcode: signing, TestFlight, visual debugging
```

In Debug, the app starts on the **demo core** (no network, the demo space shared by all apps). The launch argument
`-TomiCoreMode real` uses the real core against a local relay (`just dev-relay`, `http://localhost:8080`);
the core accepts `http://localhost` only if it is itself compiled in debug (`just apple-core --debug`).
Release always uses the real core; for a TestFlight archive, build the core with `just apple-core --no-demo`.
Signing: copy `Config/Signing.local.example.xcconfig` to `Config/Signing.local.xcconfig` (git-ignored) and set your
Apple team in it.

The **Tomi Dev** scheme (configuration `Dev`, `Config/Dev.xcconfig`) is for testing real cases on an iPhone: like
Release (real core, the space's relay, no demo files), plus the development tools (`TOMI_DEV_TOOLS`). For example, the
« Screen shared or recorded » cover offers « Continuer malgré le partage » there, for an iPhone mirrored to a Mac. This
code does not exist in a Release build: never archive Dev for TestFlight.
In Debug, `-TomiDebugScreenCaptured YES` shows this cover in the simulator.

## Relay

No relay is compiled into the repository (`TOMI_RELAY_URL` is empty in `Config/Base.xcconfig`). A device that is not in a
space gets its relay from one of these sources, in this order (`spec/pairing-v1.md` §4.4 and §10.3):

1. the link or QR code of an invitation (`https://<relay>/l/pair#<code>`) or of a creation (`https://<relay>/create#<token>`);
2. the **« Relais »** field next to the code or token (open and required without a relay, folded under « Autre relais » otherwise);
3. the build's default relay, if there is one.

A relay read from a link, a QR code or a field is **not trusted**: it is shown in full with the six-digit code
(« Relais : relay.example.org ») and, for a creation, before the token is sent. The core keeps nothing before success.
A device that is already in a space keeps its space's relay.

To build with a default relay (your own), copy `Config/Local.example.xcconfig` to `Config/Local.xcconfig`
(git-ignored) and set `TOMI_RELAY_URL = https:/$()/relay.example.org` (`$()` stops `//` from starting a
comment). The **Debug** build keeps `http://localhost:8080` (`just dev-relay`).

Links are read by the core (`CoreLinkReader`, free functions `parsePairLink`, `parseSetupLink`,
`isInstallTokenShape`): the app does not reimplement what a valid relay or link is. The app's QR scanner accepts
any relay. **Universal Links**: the host is no longer unique, so `applinks:<relay>` (entitlement
`com.apple.developer.associated-domains`) will have to be declared per build, with the AASA file served by that relay; this
is not enabled yet, only the `tomi-share://` scheme opens the app from a link.

## Privacy on screen (specific to Apple apps)

Android has `FLAG_SECURE`: a marked screen appears in neither a screenshot, a recording, nor a
mirror. iOS has no public equivalent. Apple apps therefore combine several protections, which do not exist
on Android or Windows.

1. **Capture-protected layer** (`Tomi/Common/CaptureShield.swift`). What a hidden item contains, once
   shown, is drawn in the layer of a password field (`UITextField.isSecureTextEntry`). iOS leaves it
   **empty in screenshots, recordings, mirroring and screen sharing**, and shows it normally
   on the phone's own screen. This is verified on iOS 27: the layer is a `_UITextLayoutCanvasView` whose layer
   carries the capture-exclusion marker. This is not a documented API: if a future iOS no longer provides
   a layer of this kind (the class name is checked), content is drawn normally and protections 2 to 4
   still apply. Each protected area hosts its SwiftUI content (`UIHostingController`) and follows its size.
   - Protected: the title, text, link and file list of a shown hidden item (card and detail),
     the image of a hidden item in the viewer (zoom still works), the code of a hidden file (line by line), and the QR and
     invitation code of « Ajouter un appareil ».
   - Menus: a long press on a hidden item shows a neutral preview (« Masqué ») instead of a copy of the card, and the
     « Fichiers » submenu of a hidden item never shows names (« Fichier 2 »), even when shown: a menu is drawn
     by the system, outside the protected layer.
   - Not protected: the text of a hidden item being typed in the send screen (editable field), the name of a
     hidden file in the bar and tabs of the code screen, and the six-digit pairing verification code (it
     grants nothing on its own).
   - The simulator cannot verify the effect: `xcrun simctl io screenshot` captures the screen from the Mac.
     To be checked on an iPhone (screenshot, recording).
2. **« Screen shared or recorded » cover** (`PrivacyCover`). During a recording, mirroring or screen sharing
   (`UIScreen.isCaptured`), any screen that shows a hidden item or a pairing code is covered, with
   an explanation and the steps to follow. It goes away by itself when the capture stops. Shown hidden items are
   masked again at the **start** of the capture, and only then: Face ID makes the app go through « inactive », which must
   not re-mask what Face ID has just shown.
3. **App switcher preview**. The same cover, without text, as soon as the app is no longer active.
4. **After a screenshot**, any shown hidden item is masked again (`userDidTakeScreenshotNotification`). iOS only
   announces it afterwards: it is the protected layer (1) that keeps the capture empty.
5. **Development builds** (Debug, « Tomi Dev » scheme): « Continuer malgré le partage » lifts the cover (2) for the
   current launch, for an iPhone mirrored to a Mac. The protected layer (1) stays active: the mirror shows
   empty areas. None of this bypass exists in a Release build.

## File previews

**Three levels for an image, without changing the protocol.** A thumbnail travels encrypted *inside* the item
(`spec/format-v1.md` §5.4.3, flow D20), and the relay caps its size at about 1 MiB. Several sizes therefore cannot go
in it.

| Level | Source | Used for |
|---|---|---|
| Notification | the received thumbnail, reduced to 300 px (`NotificationImage`) | the notification image (never for a hidden item) |
| Feed | the sent thumbnail (`DraftThumbnails`, as on Android): 600 × 800 at most, tall image cropped at the centre (height at most 4/3 of the width), redrawn in sRGB, JPEG 80/65/50 under 120 KB (PNG if transparent), 384 KB for the whole item, nothing for a hidden item; if the item exceeds the relay's limit, it goes without thumbnails (as on Android and Windows) | the cards, sharp at full width |
| Original | the file, downloaded on demand | the viewer (zoom to read text), copy, save, share |

No intermediate plaintext copy is kept on the device (core rule).

**Thumbnails of other files (sent by iOS).** The iOS app that sends also asks Quick Look for a thumbnail of
PDFs (first page), videos (one image), presentations, spreadsheets and Word, Pages and RTF documents, within the same
budget; never text, code or audio (an image of their text would take the budget of real images).
Quick Look gets 3 s per file, otherwise the file goes without a thumbnail, and nothing is requested for a hidden item. iOS
cards, Android and Windows show any thumbnail present; iOS adds a play button on a video.

**File viewer** (`Tomi/Features/Viewer/FileViewerScreen.swift`, iOS only: Android and Windows hand the file
to another app). Same frame as the image viewer: night background, close button and file name at the top, a
Liquid Glass bar at the bottom (or on the right on iPhone Duo) with « Partager » as the primary button, « Enregistrer dans Fichiers »,
delete, and « … » (Details).

- Depending on the type (`FilePreview`, TomiKit):
  - audio and video that iOS plays (mp4, mov, m4v, mp3, m4a, aac, wav, aiff, flac…): Apple's player, with its
    controls, audible even in silent mode; it stops when closed;
  - code: the code screen (mono, search), as before;
  - the rest, when Quick Look can draw it (PDF, Office, iWork, RTF, text, CSV as a table…): Quick Look,
    embedded in the screen;
  - otherwise (mkv, webm, avi, archives…): a page with the file and « Ouvrir dans… », the share sheet that
    offers capable apps (VLC, Infuse…).
- The file is opened under its name (with its type's extension if it has none) through a hard link in a
  temporary folder (`view-…`), erased on close, when the app goes to the background (the viewer closes then: the core
  erases its plaintext files) and at launch. Quick Look and the player read the type from the name, whereas the core's cache names files by
  item. There is no second plaintext copy.
- The file of a hidden item is never shown here, and neither is its name: Quick Look and the player draw outside the
  capture-protected layer. A page offers to share it, behind Face ID.

## Building the core

```sh
just apple-core              # or: apps/apple/tools/build-core.sh [--debug] [--no-demo]
just apple-core --no-demo    # required for a TestFlight / App Store archive
just apple-core-test         # tests of the TomiCore package on the iPhone Duo simulator
```

The script:

1. builds `tomi-core` with the features `ffi` (= `runtime` + `http` + `uniffi`) and `demo` (demo mode, removed by
   `--no-demo`) for the device (`aarch64-apple-ios`) and the simulator (`aarch64-apple-ios-sim` + `x86_64-apple-ios`,
   merged with `lipo`), as a static library (`cargo rustc --crate-type staticlib`): on iOS a Rust library
   is linked statically into the app;
2. generates `tomi_core.swift`, `tomi_coreFFI.h` and the module map with the crate's `uniffi-bindgen`
   (`--library`: the bindings are read from the archive's metadata, so they always match the compiled code);
3. assembles `tomi_coreFFI.xcframework` (one device slice, one simulator slice) and copies the generated Swift
   into `Packages/TomiCore/Sources/TomiCore/Generated/`.

Both products are git-ignored: rerun `just apple-core` after any change to `crates/core/src/ffi.rs`.
`IPHONEOS_DEPLOYMENT_TARGET` (17.0 by default) sets the minimum version for SQLite and ring, compiled by `cc`.

## Core integration rules (see `crates/core/src/ffi.rs`)

- **All methods of `RustTomiCore` block** (SQLite, HTTPS): never call them from the main thread.
- `runDoorbell()` blocks until `stopDoorbell()`: a dedicated thread while the app is in the foreground.
- `CoreListener.onChanged()` is called from a Rust thread, without a lock: re-read `items()` off the main thread,
  then publish on `@MainActor`. Keep a strong reference to the listener while it is registered.
- `CoreConfig.wrapKey`: 32 bytes **stable across launches** (Keychain, `AfterFirstUnlockThisDeviceOnly`,
  never synchronised); another key makes the database unreadable.
- `filesDir`: private folder excluded from backups; call `purgePlaintextCache()` when the app goes to the background.
- `relayUrl` must be `https://`; `http://localhost` only in a debug build (the simulator shares the Mac's network).
- `platform: "ios"` (or `"macos"`).
