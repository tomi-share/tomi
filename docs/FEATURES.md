# Tomi: feature matrix by platform

**Purpose.** A single view of what Tomi does and how each platform does it: Rust core (`crates/core`), relay
(`apps/relay`), CLI (`crates/cli`), Android (`apps/android`), iOS and macOS (`apps/apple`), Windows (`apps/windows`).
This file is used to **spot differences between platforms and keep them at zero**. The iOS implementation spec is
in `docs/archive/apple-spec-implementation.md`; the non-negotiable rules are in `AGENTS.md`. Nothing is repeated
here: this file refers to those documents.

**Last updated: 2026-11-26.**

**Maintenance rule: update this file with every new feature or behaviour change** (same commit as the code). A
feature that changes on one platform changes the row for all platforms; any new avoidable gap goes under "Open gaps".

## macOS

The macOS app (`apps/apple`, target `TomiMac`) has had its column in the tables since 17 November 2026. It is a menu
bar app (popover, full window on demand) that compiles the iOS screens: "as on iOS" in a cell means the same screen
code and the same rule (`TomiKit`), not just the same behaviour. Its description, limits and decisions are in
`docs/macos-app.md`.

A ✅ in the macOS column says that the code is there and, unless stated otherwise, that its tests pass on the Mac (the
iOS app's tests run there too, plus those of `TomiMacTests`). What nobody has tried by hand on a Mac yet is listed
under "Not validated on a device".

## Legend

| Status | Meaning |
|---|---|
| ✅ | done: seen implemented in the code (on-device validation is a separate question, see "Not validated on a device") |
| 🟡 | partial, or an accepted / known gap (the note says which) |
| ❌ | missing |
| ➖ | not applicable to this platform |
| 🚧 | in progress, or not verified ("to verify") |

Reading conventions:
- **CLI**: `crates/cli` is a shell (`tomi` only prints the version and the format bounds, 9 lines). The column is
  therefore ➖ everywhere (nothing is planned today); see "Open gaps". Relay operations go through
  `tomi-relay admin …`, which is a different CLI (local, server-side).
- **Core** and **Relay**: ➖ when the feature is purely a user-interface concern (the core does not see it) or when
  the relay is blind (it only sees opaque bytes).
- The six Android items of 10 November that are still pending on iOS are marked 🚧 "to validate on a Mac": their
  code is committed (the macOS app compiles it too), but nobody has tried it on a device.
- Abbreviated paths: `KT/` = `apps/android/app/src/main/java/eu/shaffe/tomi/`; `RS/` =
  `apps/windows/src-tauri/src/`; `FE/` = `apps/windows/src/`; `SW/` = `apps/apple/Packages/TomiKit/Sources/TomiKit/`.

## Open gaps

### A. Avoidable gaps (could be closed)

1. **Maximum number of files**: 20 (Android, iOS) versus 32 (Windows, relay). Pick a single value, put it in `spec/` and, ideally, in the core.
2. **Total 100 MB check in the core**: only the number of blobs is checked before sending; an oversized item is refused only by the relay (queue behaviour to verify).
3. **Triple secret detection**: three heuristics (Android, iOS, Windows) with different thresholds (512 / 128). Factor them into the core, or align them with shared test vectors.
4. **Windows: the clipboard "sensitive" flag is never read** (`flagged_sensitive()` is dead code): a password copied from a password manager is not locked to "Masquer" (hidden).
5. **Windows: no "Options" button** on the undo banner (Annuler only); to decide whether the composer is enough.
6. **Windows: no "Hors ligne · en attente" (offline · pending) chip / banner** (Android has it; iOS 🚧).
7. ~~**Inactive-device hint**: iOS does not have it yet~~ — done (`DeviceInactivity` in `TomiKit`, shown by the shared `DevicesScreen` on iOS and macOS). Still not tried against a real relay on any platform.
8. **Windows: no "Réinitialiser" (Reset) for a database without a key** (Android and iOS have it, with confirmation).
9. ~~Windows: the 2-minute Hello window is not closed on session lock / sleep~~ — done (`session_watch.rs`).
10. **Windows: plaintext copy kept for 1 minute** after last use (golden rule 3: background or startup). The feed snapshot of the bridge (`RealCore.snapshot`) now holds only a keyed fingerprint per item, but the core still decrypts the whole feed at each pass and the DPAPI-unsealed key stays in memory: a real fix needs the "sealed secrets" design in the core.
11. **Code screen: different language lists** (Android: tree-sitter, 14 languages + PHP; iOS and macOS: `CodeHighlighter`, 15 grammars plus 9 more; Windows: ~12 languages); align them. (iOS now has syntax colours.)
12. **iOS: no universal links** (`applinks:` absent): depends on the signing team and an AASA route to add to the relay.
13. **iOS: no widget / send control** (Android: tile); whether it is useful is still to be decided.
14. **iOS: no TestFlight and no delivery (CD)**, the archive action of the `Tomi Dev` scheme uses `Release` (no developer tools); the Apple CI only builds and tests (never run yet: validate the three jobs on a first push).
15. **Android: no FCM push**, although the relay can send it and the core can register a token (`register_push`): what is left is adding Firebase to the Android app and calling `registerPush("fcm", token)`.
16. **Android: OFL font licences missing**, R8 / minify disabled, no release signing, Markdown rendering hardening still needed before a public release.
17. **Android: unconditional background clipboard clearing** (it may overwrite a more recent copy); background purge of the plaintext copy to verify.
18. ~~**`device_set_mismatch` alert** not exposed by the core~~ — done (`rotation_stalled()` and a calm banner on every app, see §11).
19. **Release and CI**: Android and Windows (APK / installer) are delivered by hand, without a reproducible workflow; CI of `apps/windows` limited to `npm run check`, the front-end build and `cargo test` (`windows-app` job, no clippy, no installer); no artifact signing (relay included).
20. **Windows: no updater** (`createUpdaterArtifacts: false`).
21. **Windows: texts written by hand** (`fr.ts`) instead of derived from `strings.xml` (drift possible).
22. **Theme**: no manual Light / Dark setting on Android and iOS (Windows has one).
23. **PDF / video / Office thumbnails** produced only by iOS (Android and Windows send without them).
24. **Device name input limits**: 40 (Android, iOS) versus 64 (Windows).
25. **Check that Windows' manual history transfer** (Devices tab) is not a gap with mobile (which only do it at pairing).
26. **`tomi` CLI**: a shell with no commands, while `PROJECT.md` and `api-v1.md` (`watch` mode) describe it; ship it or remove it from the docs.
27. **Incomplete spec**: expiry options, the 20-file limit and the thumbnail ceiling are not in any spec; `tomi-share://send|item|open` only appears in `docs/`.
28. **Outdated docs**: `apps/windows/README.md` (undo "5 s": the code says 3 s), Android comments ("5 s"), `justfile` (comment "spec_vectors.rs pas encore" (not yet)), `docs/multi-person-shared-relay.md` (describes a single-space relay although `spaces.rs` exists).
29. **Six iOS 🚧 items** (3 s undo, send date, `SeenTracker`, bar that no longer hides, selected button, file cards): the code is committed; to validate on a Mac or an iPhone, then tick them ✅.
30. **macOS: no drop on the menu bar icon** (dropping works on the popover and the window); no `⌘O`, `⌘S`, `⌘⌫`, `⌘Z` shortcuts (the actions are in the bar and the menus); no "My space" entry in the Settings (leaving is in the "⋯" menu of the feed). No organised distribution either (built and signed on the maintainer's Mac, no TestFlight), and the Mac app's tests run unsigned in CI (keychain and app group not tested there).
31. **macOS: App Nap not handled**: with no window open, macOS may slow the app down (doorbell less responsive, the one-minute purge of plaintext copies taking longer); the fallback sync every 5 minutes bounds the delay.
32. **iOS and macOS: opening a `tomi-share://` link and clicking a notification are not tested at the app level** (such a test would touch the machine's real app group); link parsing and notification content are.
33. ~~**macOS: the "New device added" notification never fires**~~ — done (`AppContainer.isOnScreen` uses `surfaceVisible` on the Mac).

### B. Gaps imposed by the platform or an external dependency

| Gap | Reason |
|---|---|
| iOS cannot prevent a screenshot (no `FLAG_SECURE`); `CaptureShield` relies on the undocumented behaviour of a password field | iOS has no equivalent public API; compensated by `PrivacyCover`, re-hiding after a capture, and protections 2 to 4 in `apps/apple/README.md`. |
| iOS: a secret item cannot be kept off the lock screen (`VISIBILITY_SECRET`); the notification only shows "Tomi : nouvel élément" (Tomi: new item) | No iOS equivalent; content is never put in the notification. |
| iOS: a push can only show a fixed text ("Tomi · New item") until the app has been woken | The relay does not see the content; iOS wakes the app when it wants to, never if it was closed by swiping it away. Needs the APNs key of the Apple developer account on the relay. |
| iOS: the share extension cannot open the core or launch its app | iOS extension limitation; worked around with the App Group inbox `ShareInbox`. |
| iOS: "strong" biometrics = Face ID / Touch ID only (no "strong only" notion as on Android). Android accepts the screen lock (PIN) for revocation, deletion, erasure and adding a device, so that a lost phone can still be dealt with | Decided by the maintainer (PR-10) for iOS; no exact equivalent exists. Aligning iOS on the passcode is an open decision. |
| iOS: no source-app identifier and no clipboard "sensitive" marker in a share | The extension cannot see them; only the content heuristic applies. |
| macOS does not say that a screen is captured, recorded or shared: no "Screen shared" cover, no re-hiding after a capture | No public API; instead the whole window is excluded from captures (`NSWindow.sharingType = .none`) while it shows a sensitive screen, and a revealed secret item hides again after 15 s. |
| macOS: no background tasks and no push; with Tomi quit or the Mac asleep, nothing arrives | The app stays open in the menu bar (open at login); it catches up on wake, on network return and every 5 minutes. |
| macOS: the app must be signed with a team and a profile | The data protection keychain (wrapping key) and the app group require it; a badly signed build says so on screen. |
| macOS: no swipe to archive, no mosaic in a wide window | Intended (decision A2 and following in `docs/macos-app.md`): card menu and Detail bar, readable column. |
| Android: no standard FileProvider (in-house `AttachmentProvider`, not exported) | Technical choice, not a functional gap. |
| Windows: no camera QR scanning | PCs usually have no useful camera; the code is typed or the link is pasted. |
| Windows: no share extension and no swipe-to-archive | No Windows equivalent of the share sheet; the ⋮ menu replaces the swipe (by design). |
| Windows: `https://…/l/…` links not handled | Windows does not launch the app from an https link; it is pasted into the field. |
| Windows: an ongoing Hello prompt is not cancelled on session lock | The window of a verification is closed on lock and sleep (`SecretGate::close`), and a prompt that was on screen then does not open it; the prompt itself is Windows' and stays until dismissed. |
| Core: metadata (ids, dates, flags, sizes, device names) stays in plaintext in SQLite | Accepted trade-off, listed in `runtime/store.rs`; no content and no title. |
